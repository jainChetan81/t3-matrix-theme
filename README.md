# Matrix theme for T3 Code

A green "digital rain" theme for T3 Code in the **Possessed** direction from the Claude Design rounds: a sparse glyph field falling behind the whole conversation, a phosphor-terminal chrome, and short one-shot effects when a thread opens or a reply arrives. Prose stays in the app's sans on a dark pocket, so it reads comfortably all day, and the idle cost is about 15 ms of main thread per 5 s.

Screenshots from the real app (T3 0.1.10) are in `design/verify/`; see "Verify".

## Install

```sh
t3 theme set ./matrix.json            # VPS: t3 is on PATH
~/.t3/bin/t3 theme set ./matrix.json  # Mac
```

`theme set` with a file publishes the theme and selects it in one step. Undo by selecting another theme: `t3 theme set pixel-quest-plus`, or a built-in: `t3-chat`, `grove`, `ocean`, `ember`, `iris`.

## Build

```sh
python3 -I build.py
# css 15546/20000 chars, file 18075/32768 bytes, svgs: prompt, rain, spinner
```

`build.py` minifies `src/theme.css` (quoted strings are left untouched), inlines `src/*.svg` as `data:` URLs, adds the colour roles from `src/colors.json` and writes `matrix.json`. It fails the build if the theme breaks a T3 limit: CSS over 20,000 chars, file over 32 KB, a `url()` that is not `data:` or `#id`, `@import`, `image-set()`, `src()` or a backslash.

| file | what |
|---|---|
| `src/theme.css` | all rules, commented by section |
| `src/colors.json` | 61 colour roles (dark only) |
| `src/rain.svg` | 1000x650 still tile on a 25 px grid: 14 short streams (light head, fading trail) and about 70 loose glyphs. Generated by `python3 -I design/gen-rain.py [seed]` |
| `src/prompt.svg` | the composer prompt chevron |
| `src/spinner.svg` | 14 px glyph cycler from the Possessed kit |

## The look

- **Typography.** Monospace for the chrome: sidebar, header, user bubbles, composer, work-log rows, tooltips, menus and popovers. Assistant prose stays sans; inline code is mono.
- **Rain.** One sparse tile at three depths. A still field (the tile at 40% under an 84% wash) is the background of the conversation and the sidebar. Two moving layers cover the whole conversation: near (25 px cells, 125 px/s, opacity .5) and far (the tile at 60%, 33 px/s, opacity .34), both `steps(26)` so glyphs move one cell at a time.
- **Reading column.** A horizontal mask cuts both moving layers to 20% under the reading column plus a 20 px gutter, fading over 110 px, so the effective opacity under prose is about .10 / .07. The column is computed from T3's `--chat-content-max-width` and lane insets, so the "wide" and "full" chat widths and an overlapping panel are followed. Assistant messages also sit on a dark pocket (`#030a07` at 85%, extended 14 px sideways with flat shadows, no blur).
- **New thread.** The draft screen keeps 53% of the rain under the column; the composer card is opaque and stays clear.
- **Dim while typing.** While the composer is focused and has text the layers drop to .17 / .11.
- **Panels.** User bubble, composer card, code panes, menus, popovers and dialogs have a green hairline and a soft static glow. Code panes are CRT tubes: 12 px radius, radial dark-green background, static scanlines and vignette. Code text has no glow.
- **Composer.** Drawn `❯` chevron, mono input, block caret while empty (blinks ten times after focus, then stays lit). The outline is T3's own ring recoloured through `--chat-composer-outline`, brighter on focus.
- **Sidebar.** The active row is a green outline box; hover is instant and fades out over .9 s; project monograms are green-bordered tiles. A running thread gets a slow sheen and its status icon becomes the glyph spinner.
- **Tooltips** are green with dark ink and type on. **Selection** is the accent inverted. **Scrollbars** only change colour (a dim green thumb).

## Motion

| effect | trigger | length |
|---|---|---|
| rain, near and far | always (off under 62rem window width) | loop |
| roll bar: a faint 140 px band crossing the window | always | loop, 16 s, 72 steps |
| sheen on a sidebar row | only while that thread is working | loop, 2.4 s |
| the line: a scan band sweeps down the conversation | thread opens | .9 s once |
| title glitch | thread opens | two .08 s jumps, once |
| active sidebar row flicker | thread opens | .25 s once |
| rows flicker in | a row mounts (thread open, new message) | .5 s once |
| decode: bright glyphs on a dark plate step away over the new reply | a reply starts streaming | .8 s once |
| scan-line wipe down the whole reply | the reply finishes streaming | .65 s once |
| menus and popovers flicker in, dialogs power on, tooltips type on | on open | .25 to .4 s once |
| caret blink | composer focused and empty | ten times |

How the two triggers that are not plain mount animations work:

- **Thread open.** In T3 0.1.10 nothing above the message rows remounts when you switch threads, so a mount animation cannot fire. Sixteen rules set a custom property `--n` on the sidebar wrapper from the last hex character of the active sidebar row's id. The scan line and the title use `animation-name: var(--n)`; a different thread gives a different name, which restarts them. The sixteen `@keyframes` are identical and read their start values from the element (`--a`, `--b`), so one set serves both effects. Two threads whose ids end in the same character (1 in 16) do not replay it.
- **New reply.** The markdown root carries `data-streaming` while a message streams. The decode is an animation keyed on that attribute, so it starts once when streaming starts and is not replayed by text updates. The wipe is a *transition* that runs when the attribute goes away, so it never plays on mount or on thread open.

Reduced motion: every animation and transition the theme adds is switched off by a scoped selector list (not `*`), the rain stays as a still image and the spinner goes back to T3's icon. Checked in the real app: 0 running animations.

## What changed from the Possessed kit, and why

- **Rain under prose is masked down** instead of running at full strength behind 87% pockets, and the pockets have no 34 px blurred shadow (a paint cost on every row while scrolling).
- **The sidebar rain is still.** The kit animated two more layers there; a still field gives the same texture with no loop.
- **Slower rain** (125 and 33 px/s instead of 176 and 48) and softer text (`#c9e2d4` on `#030a07`, about 14:1) for all-day use.
- **The glitch runs once per thread open** instead of every 11 s, and without the animated red/cyan `text-shadow`.
- **No `filter: drop-shadow` on icons, no text glow on code or headings, no glowing scrollbar.** The only text glow is on the one-line header title.
- **The roll bar is stepped** (see Performance).
- **The per-row scan line became one line for the whole conversation** on thread open, plus the wipe on a finished reply. Row containers in T3 have paint containment, so a row cannot draw outside itself anyway.
- **Stagger.** The kit staggered the last three rows with `:nth-last-child`. T3's timeline is a virtualised list where every row is the only child of its own lane, so that selector is meaningless; assistant rows are delayed .08 s after the others instead.

## Performance

Rules the CSS follows: every loop is a `transform` on its own layer; the rain is a still SVG moved with `steps()`; nothing animates inside the rain tile and `background-position` is never animated; no filters, no blur, no animated `text-shadow`; glow is a static `box-shadow` on a handful of panels.

Running animations per state (`document.getAnimations()` in the real app):

| state | running |
|---|---|
| thread, idle | 3: rain x2, roll bar |
| draft, idle | 3 |
| composer focused and empty | 4 for 11 s (caret blink), then 3 |
| typing | 3 |
| thread just opened | 3 + scan line, title glitch, row flicker per row; all finished within 1.3 s |
| reply just arrived | 3 + row flicker x3 (.5 s), decode (up to .8 s), then the wipe (2 transitions, .65 s); back to 3 |
| thread working | 3 + sheen, plus T3's own two live-activity animations and the 14 px spinner |
| window under 992 px | 1 (roll bar) |
| reduced motion | 0 |

Measured in the real app (T3 0.1.10, throwaway instance) in headless Chrome at 1512x900 on a Linux VPS, 5 s traces. This Chrome has no GPU (SwiftShader), and the machine was loaded (load average 3.6 to 5.6 on 4 cores), so treat frame rates as relative. "idle" is the page left alone; "busy" adds a `requestAnimationFrame` loop so Chrome produces main frames continuously, as it does while a reply streams. Main thread = style + layout + prepaint + paint + commit.

|---|---|---|---|---|---|---|---|---|
| thread, no theme | idle | 0.0 | 0.3 | 2.3 | 4.8 | 7.5 | 2.0 | 0 |
| thread, Matrix | idle | 4.3 | 1.9 | 1.4 | 9.0 | 16.7 (14.4 to 16.7, four runs) | 15.6 | 3 |
| thread, Matrix, caret blinking | idle | 17.0 | 3.5 | 0.0 | 11.6 | 32.0 | 15.4 | 4 |
| draft, no theme | idle | 0.0 | 0.2 | 0.0 | 2.7 | 2.9 | 2.0 | 0 |
| draft, Matrix, caret blinking | idle | 48.9 | 3.5 | 0.0 | 16.9 | 69.3 | 15.4 | 4 |
| typing, Matrix | idle | 4.6 | 1.5 | 0.0 | 8.4 | 14.4 | 14.8 | 3 |
| reference canvas page | idle | 0.0 | 13.6 | 0.0 | 355.9 | 369.5 (370 to 548, two runs) | 24.6 | canvas |
| thread, no theme | busy | 31.9 | 26.9 | 52.5 | 192.3 | 303.6 (273 to 364, five runs) | 59.4 | 0 |
| thread, Matrix | busy | 34.5 | 18.6 | 22.4 | 93.6 | 169.2 (169 to 310, seven runs) | 34.8 (12 to 37) | 3 |

What this means:

- **Idle** the theme costs about 15 ms of main thread per 5 s, about 9 ms over the unthemed app and about 25 times less than the reference canvas page. The caret blink roughly doubles that for the 11 s it runs, and more on the draft screen.
- **Busy**, the per-frame main-thread cost is about the same with and without the theme (about 1.2 ms per main frame). The totals are lower with the theme only because fewer frames were produced.
- **Frame rate under load drops** from 60 to roughly 30 frames/s in this GPU-less Chrome. The cause is compositing the two full-area masked rain layers on the CPU: with the rain layers removed it is back to 51 to 59. A static dark veil in place of the mask measured the same within noise. A real GPU composites these layers in well under a millisecond, but it has not been measured on one; if the Mac shows dropped frames while streaming, the first thing to try is removing the far layer.
- **Roll bar.** A smooth (linear) roll bar made the compositor draw 46 frames/s at idle, against 8 without it. Stepped (`steps(72)`, about 4.5 moves a second while it crosses) it draws 15 frames/s and adds no measurable main-thread time (16.7 and 14.9 ms with it, 16.7 and 14.2 without), so it stays as a loop.
- The reference page was measured over the network from `https://chetan-examples.vercel.app/matrix`.

## Verify

The harness drives a throwaway T3 server and its own headless Chrome (see the docstring of `design/verify/real/shoot.py`; it needs the `websocket-client` Python package). It never touches the live T3.

```sh
python3 -I build.py
python3 design/verify/real/shoot.py reload-theme
python3 design/verify/real/shoot.py shot thread --action 'thread:Matrix rendering one' --action nopanel
python3 design/verify/real/shoot.py burst open --action 'thread:Matrix python notes' --thread 'Matrix rendering one' --rate 0.12 --shots
python3 design/verify/real/shoot.py arrive --rate 0.15      # sends one real message
python3 design/verify/real/shoot.py bench thread --action 'thread:Matrix rendering one'
```

`burst` and `arrive` print the animations alive at each frame, and `--rate` slows CSS animations so screenshots can catch sub-second effects.

## Fragile selectors

These depend on T3 internals that have no stable hook. If a T3 update breaks the look, check them first. `design/verify/real/dom-notes.md` records what was seen in 0.1.10.

- `[data-slot="sidebar-wrapper"]:has([aria-current][data-sidebar-row$="…"])`: the thread-open trigger. It needs the active sidebar row to carry the thread id in `data-sidebar-row` and the id to end in a hex character. If it stops matching, the scan line and the title glitch simply never play.
- `[data-assistant-citation-viewport]`: the non-scrolling parent of the timeline scroller; its `::after` is the scan line.
- `.chat-markdown[data-streaming]`: the streaming hook for the decode and the wipe.
- `[data-sidebar-row][aria-label*=", Working,"]` and `.lucide-circle-dashed`: how a running thread is detected. The label text is English.
- `[data-workspace-area="conversation"]:has(> [data-timeline-loading])`: how "new thread or still loading" is detected. `[data-timeline-loading]` is made transparent so the rain shows through.
- `[data-timeline-row-kind] > .border-b`: the work-log hairline, a Tailwind class.
- `[data-chat-header] li[aria-current="page"] [data-slot="workspace-breadcrumb-text"]`: the thread title.
- `[data-chat-composer-form] :has(> * > .composer-tiptap)`: the editor's grandparent, which carries the prompt and the block caret. Its child `.pointer-events-none` is the placeholder.
- `.composer-tiptap:has(> p:only-child > br:only-child)`: "the editor is empty". The typing dim uses the same test, negated.
- `--chat-content-max-width`, `--chat-lane-inset-start`, `--chat-lane-inset-end`: T3's lane geometry. If renamed, the mask falls back to a 46rem column.
- `--chat-composer-outline` on `[data-slot="composer-host"]`, and `[data-chat-composer-surface]` made transparent so the host's gradient shows.
- `.chat-content-lane { overflow-clip-margin }`: lets the reading pocket extend past the lane's horizontal clip.
- The theme owns `::before` and `::after` on the conversation area, on assistant `.chat-markdown` and on the composer grandparent, and `::after` on the citation viewport, the chat header, code blocks, tooltips and running sidebar rows.

## Not verified

- **Long threads.** The test instance has no thread long enough to make the virtualised list remount rows while scrolling (a 1236 px timeline in a 380 px window remounted none). If rows do remount in view on a fast scroll, they will flicker in; the fix would be to limit the flicker to user bubbles.
- **A real GPU / the Mac app.** All numbers are from software compositing on a VPS.
- **A long streamed reply.** The model in the test instance (Haiku) streamed each reply in under a second, so the decode was cut short by the wipe in the real runs; the full decode was only seen by setting `data-streaming` by hand.
- **`lucide-loader` icons.** None appeared in any state seen; the spinner rule for them is untested.
